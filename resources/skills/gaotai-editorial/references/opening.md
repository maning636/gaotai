# 开头三行

公众号读者在手机上滑走的决定，通常发生在读到第三行之前。开头三行不是文章的装饰，
是唯一一次把读者留下来的机会。

## 适用场景

- 一篇稿子的开头写完但自己读着没劲。
- 数据不错但完读率很低（说明开头没留住人）。
- 要给一篇长稿写导语。

## 判断标准

开头三行必须同时做到：

1. **不铺垫**：不出现「背景」「众所周知」「随着」「近年来」「在这个……的时代」。
2. **给出理由**：读者为什么要继续读——是一个具体场景、一个反常识结论、
   还是一个他正在纠结的问题。
3. **不含信息量低的句子**：删掉任意一句而不影响理解，那就删掉。

## 三种可用的开头

**场景开头**：直接进入一个具体的时刻。
> 周三下午四点，监控面板突然红了。不是流量涨了——是那个跑了两年没动过的定时任务，
> 把同一批订单提交了三次。

**结论开头**：把答案放在最前面，理由放后面。
> 这个方案在 500 人以下是浪费，在 5000 人以上是必需。分界线不在技术，在你有没有一个
> 能随时接管的运维。

**冲突开头**：给出两个看起来矛盾的事实。
> 官方文档说这个 API 最多支持 200 QPS，我们压到 1800 也没事。问题出在代理层，
> 不在 API。

## 反例

- 「在当今社会，效率已经成为每个人都需要关注的核心议题。」——零信息量。
- 「相信很多朋友都遇到过这样的情况……」——替读者发言，读者不需要你代言。
- 「今天我们要来聊一个很有意思的话题。」——不说是什么话题。

## 常见毛病

- **先介绍文章结构**：「本文将分为三个部分……」读者不想知道。
- **先致谢**：「感谢大家一直以来的支持。」读者不知道为什么该感谢。
- **先定义名词**：把读者都知道的概念解释一遍。
- **太用力**：第一句就金句，后面接不住。开头的高度决定全篇的预期。

## 执行步骤

1. 把开头前三句单独拎出来，删掉所有「介绍性」的句子。
2. 检查剩下的内容是否同时满足上面三条判断标准。
3. 如果开头在铺垫，试试从正文中间找那个最有画面的场景，把它提到最前面。
4. 写 3 个不同类型的开头（场景 / 结论 / 冲突），挑一个。
5. 把开头接到正文第一段上读一遍，确认没有重复——开头说过的话，正文不要再说一遍。
6. 移动端预览：开头三行在手机上一屏之内。
