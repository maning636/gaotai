# 架构判断：枪手 skill 能撑起多少，要不要调格局

> 这份文件回答三个问题：枪手 skill 能不能丰富整个过程 / 能不能解决「大纲到输出文案」的问题 / 整个格局要不要调架构。
> 结论先写，后面是证据。

## 结论

1. **枪手 skill 能丰富正文，但不能承担流程。** 它在稿台里的正确位置是「写法的来源」，
   不是「流程的编排者」。稿台**不该**内置它（PolyForm Noncommercial，禁商用），
   该做的是把接口留好，让用户把自己的方法按稿台的格式放进来。
2. **「大纲到输出文案」的瓶颈不是方法不够，是正文请求里塞了太多不该塞的东西。**
   把字数账、技能包清单、选题阶段全文这三样去掉之后，同样的 skill 写法从
   「533 秒交 0 字」变成「15.9 秒交 860 汉字，一次成」。
3. **格局要调，但不是推翻重来，是三处调整**（都已落地）：
   工序之间只传骨架、质量从闸门改成报告、方法与流程各归各位。
   四道工序的结构本身不动——每一道工序后面都有人工的签字点，这是它成立的理由。

## 一、枪手 skill 能丰富整个过程吗

### 能，但只在正文的第一稿

稿台现在的做法：**正文阶段一个工具都不给**（连 `check_prose` 也不给），
服务端只把技能包里「第一稿直接带着人写」那一节抽出来注入提示词。

这不是偷懒，是被真模型逼出来的：

| 做法 | 真模型实测 |
| --- | --- |
| 正文阶段挂工具循环 | 模型先读 15KB 的 SKILL.md、再读 24KB 的 reference，每轮重发越来越大的上下文 → **10.3 分钟换 0 字** |
| 整份技能包注入 | 里面有「先列清单再动笔」「写完自查再改」这类**程序型指令** → 模型逐条核对，思考额度吃光 |
| 只注入「第一稿带着人写」 | 一次成稿 |

所以 skill 在稿台里的三件事边界很清楚：

| 活 | 谁干 | 为什么 |
| --- | --- | --- |
| 「这一段怎么写才有个人味儿」 | 技能包（方法） | 方法给路，禁令只给墙 |
| 「什么时候写、写多长、失败了怎么办」 | 代码（流程） | 写进提示词就变成模型要核对的任务 |
| 「这一篇长什么样」 | 排版模板（用户自己沉淀） | 跟写作方法无关，不该混在一起 |

### 能加的两个位置

- **材料解读阶段**：`skillStages = ["brief", "article"]` 已经开着。
  用户自己的「总结 skill」挂在这儿才有用——输入两三千字 → 压成能用的 brief → 后面才写短稿。
- **大纲阶段**：skill 的方法可以借（怎么定「谁在说」、怎么定推进线），
  但**同样不能带工具**。大纲阶段带工具，模型会去读文件，额度又会被吃光。

### 承担不了的

编排工序（确认闸门、上下文裁剪、失败重试）、质量兜底（体检、覆盖度）——
这两样是产品的活。skill 是「怎么写」，不是「写没写对」。

### 所以「丰富整个过程」的正确加法

不是往稿台里塞更多 skill 或更多字数指令，而是：

- 稿台**提供接口**：技能包机制（`resources/skills/<id>/SKILL.md` + `references/`）+
  正文阶段注入点。用户把自己的枪手 skill 按格式放进去就能用。
- 稿台**可以自带几套原创方法卡**（像 `gaotai-editorial` 那样），
  按「哪道工序用」分类。现在只有一个注入点（正文的第一稿），
  可以扩到「开头」「结尾」「标题」三个位置。

## 二、能不能解决「大纲到输出文案」的问题

**这一轮最大的收获是：大纲到正文的问题，主要不是 skill 不够好，是稿台自己给的东西太多了。**

### 三样最伤人的东西

| 塞进正文请求的东西 | 后果 |
| --- | --- |
| **字数账**（「篇幅」节 + 每节字数预算 + 程序型核对指令） | 模型逐条核对，思考额度吃光 |
| **技能包清单**（含「用 read_skill_file 读入口文件」「改用 check_prose 工具做同一件事」） | 正文阶段一个工具都不给，这些是程序型指令，模型会去调工具 |
| **选题阶段全文** | 上下文是交付物的 14 倍 → 陷进长上下文的思考 |

### 实测对照

| 改法 | 正文结果 |
| --- | --- |
| 旧：字数指令 + 技能包清单 + 选题全文 | 533s / **0 汉字** |
| 加大额度救（8192 → 16384） | 仍然 0 字（`reasoning_tokens == max_tokens`，额度不是杠杆） |
| 去掉这三样 | **15.9s / 860 汉字 / `finishReason=stop`，一次成** |

真模型：`sensenova-6.8-flash-lite`，`reasoningEffort=minimal`，
项目 `prj_3861152d33c94d64aea372be38f9fd55`（`.tmp/real-run-24`）。

**结论**：skill 的那一节方法就是最好的燃料，它不需要再加工。
加工的是稿台自己——**正文请求里不该有的东西，比该有的更致命**。

### 剩下的没解决的部分

- **大纲阶段仍然慢**（240s）。它要一次定下「谁在说 + 全文推进线 + 每段的推进/素材/形式」，
  这个信息量本来就大，慢是合理的。
- **大纲曾经比正文长一倍**：每段「内容」字段写成了 236 字的散文——
  模型在大纲阶段就把正文写了一遍。现在限到 ≤35 字，并明令禁止写行文指导。
- **说话位置四行不齐时，稿台不替模型编**：退回「按一个真正干过这行的人写」。
  这是明确的失败姿态，不是兜底——替模型编一个说话人，比没有更坏。

## 三、格局要不要调架构

要调，三处。都已落地。

### 调整一：工序之间只传骨架

每道工序只向下游交出「骨架」：材料交硬事实、选题交一个角度、大纲交推进线 + 说话位置 + 分段。
**不交全文。**

通用规律：任何「多工序 + 中间产物」的系统，都要问一句「**中间产物比交付物长吗**」。
长了就是设计错了：要么给中间产物设独立预算，要么在下一阶段只取结构不取全文。

### 调整二：质量从闸门改成报告

原来的闸门链（整篇重写 → 按句改写 → 按节补写 → 两版挑一版）在真模型上是**负收益**：

1. 整篇重写和按节补写极不可靠——额度全被思考吃光，等一圈下来什么也没改成。
2. 改写会顺手把稿子改短、改钝（实测：冒号少了但字数更短了）。
3. 用户要的是一份能自己判断的稿子，不是一份被机器来回搓过的稿子。

现在：体检只报不改。合格线是「大纲要点覆盖」，不是字数。
字数目标仍然算出来给用户看（材料撑不起就写短，写短是合法的），但**不作合格线、不触发改写**。

通用规律：**机器搓过的稿子，不如人自己改的稿子**。

### 调整三：方法与流程分开，各归各位

| 归谁 | 装什么 |
| --- | --- |
| 技能包 / 提示词 | 「怎么写」——方法 |
| 代码 | 「什么时候写、写多长、失败了怎么办」——流程 |
| 排版模板 | 「这一篇长什么样」——用户自己沉淀的资产 |

### 不用动的

- **四道工序的结构本身**（brief → angle → outline → article）。
  它成立的理由是每一道工序后面都有人工的签字点：
  草稿不注入下游，避免把草稿当定稿。
- **中间产物的独立字数预算**（大纲 700 / 选题 700 / 材料解读 800）。
  模型分不清「正文多长」和「这份大纲自己多长」，不给具体数字它就按前者来。

## 附：这一轮踩过的坑（通用）

1. **「实机点通过」不等于「这条链路真的通」。**
   清洗器把样式值里的 `{{变量}}` 连同整条声明丢掉，导入样式包的部件**悄悄没了样式**且不报错——
   而浏览器实机点测看着完全成功（改色值后 7 处跟着变），
   因为**默认部件模板也引用同一个变量**，默认路径把被测路径的效果盖住了。
   → 验证被测路径时要用**只有它能产生的**值（专用变量名、专用 id、专用色值）。
2. **断言不能只看关键词。**「正文请求里不能出现『控制在』」会误伤材料里的
   「标题长度控制在 20 字内」和「监控」里的「控」。要写成上下文敏感的形态。
3. **规则清单 / 程序型指令是思考螺旋的燃料。** 方法给出路，禁令只给墙。
