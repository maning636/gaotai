# 稿台项目踩坑知识库

> 本文档记录稿台项目开发过程中遇到的真实问题、根因分析和预防措施，供后续项目避雷。

---

## 1. Next.js Standalone 打包陷阱

### 1.1 Turbopack 漏追踪运行时依赖

**现象**：安装包在用户机器上所有 API 路由返回 500（`Cannot find module`），但开发机上完全正常。

**根因**：Next.js 16.4.2 用 Turbopack 构建时，App Router 的路由运行时 `next/dist/compiled/next-server/app-route-turbo.runtime.prod.js` 不会被打进 `.next/standalone/node_modules/next/`。开发机上 Node 会逐级向上找 `node_modules/next`（项目根的完整包），所以 require 成功；装到用户机器后 standalone 上面再没有完整的 next 包，require 直接抛错。

**预防**：
- 打包后必须跑 `scripts/ensure-runtime-deps.mjs`，它扫描 standalone 产物里所有外部 require，逐个检查能否解析到实体文件，解析不到的从项目 node_modules 补进去
- 不要只靠开发机测试判断"能跑"——standalone 的依赖链和开发态不同
- 每次升级 Next.js 版本后重新验证 standalone 产物完整性

### 1.2 Turbopack 把敏感文件拉进 Standalone

**现象**：安装包里包含 `.env`（真实密钥）、`data/`（个人文章库）、源码树。

**根因**：Turbopack 的文件追踪会把整个项目拉进 `.next/standalone/`。实测 `outputFileTracingExcludes` 压不过 Turbopack 的追踪行为。

**预防**：
- 打包前必须跑 `scripts/sanitize-standalone.mjs`，白名单只保留运行时真正需要的条目
- 打包后跑 `scripts/verify-package.mjs` 扫描安装包里有没有密钥、数据库、授权令牌
- `.env` 永远不进安装包——用户数据目录的 `.env` 由首次运行时生成

### 1.3 Standalone 里的符号链接

**现象**：`sanitize-standalone.mjs` 报错退出：产物中存在符号链接，无法安全打包。

**根因**：Next.js Turbopack 在 `.next/node_modules/` 里创建指向项目 `node_modules/` 的符号链接（如 `better-sqlite3-90e2652d1716b047 -> ../../node_modules/better-sqlite3`）。打包时这些符号链接会断裂。

**预防**：
- 脚本链顺序必须是：`copy-standalone-assets`（清符号链接）→ `sanitize-standalone`（清理敏感文件）→ `ensure-runtime-deps`（补依赖）→ `prepare-resources`（准备资源）→ `electron-builder`
- `copy-standalone-assets.mjs` 会把符号链接替换为实体文件 shim
- `npm run desktop:build` 里的脚本顺序不能随意调整

### 1.4 构建管道缓冲问题

**现象**：`npm run desktop:build`（`npm run build && electron-builder`）卡住数分钟无输出。

**根因**：Next.js build 和 electron-builder 串行执行时，管道缓冲导致输出延迟。分步执行（先 build，再单独跑 electron-builder）可以正常完成。

**预防**：
- 如果 `npm run desktop:build` 卡住超过 5 分钟，分步执行各脚本
- 分步执行顺序：`npm run build` → `copy-standalone-assets` → `sanitize-standalone` → `ensure-runtime-deps` → `prepare-resources` → `ELECTRON_BUILDER_OFFLINE=true npx electron-builder --win` → `verify-package`

## 2. Electron 环境差异

### 2.1 GAOTAI_LICENSE_BYPASS 安全剔除

**现象**：开发时 `.env` 里设了 `GAOTAI_LICENSE_BYPASS=1` 可以跳过授权，但安装包里授权检查始终生效。

**根因**：`electron/main.js` 第451行 `delete baseEnv.GAOTAI_LICENSE_BYPASS`——后端子进程的环境变量里会被显式剔除这个值，防止授权门禁被绕过。

**预防**：
- 开发时用 `GAOTAI_LICENSE_BYPASS=1` 没问题，但不要指望它能进安装包
- 安装包的授权必须走真实流程（注册码 + 服务器验证）
- 测试安装包时需要在用户数据目录配置授权服务器或使用有效注册码

### 2.2 Electron Node 版本 vs Standalone Node 版本

**现象**：某些原生模块（canvas、better-sqlite3）在 dev server 正常但在安装包里加载失败。

**根因**：Electron 内嵌的 Node 版本和 standalone 产物的 Node 版本可能不一致。原生模块（`.node` 文件）是针对特定 Node ABI 编译的。

**预防**：
- `electron-builder.yml` 里设 `npmRebuild: false`，用预编译二进制而不是现场编译
- better-sqlite3 用 `prebuilds/` 目录里的预编译二进制
- canvas 需要确认 `build/Release/canvas.node` 在 standalone 里存在
- 每次升级 Electron 版本后验证原生模块兼容性

## 3. 前端 JSON 解析崩溃

### 3.1 裸 response.json() 空响应崩溃

**现象**：浏览器报 `Failed to execute 'json' on 'Response': Unexpected end of JSON input`，操作中断。

**根因**：后端 API 在某些异常情况下（进程崩溃、原生模块加载失败、超时）返回空 body（HTTP 200 但无内容），前端 `await response.json()` 解析空字符串直接抛异常。如果 没有 try-catch 包裹，整个函数中断，用户看到的是"推送失败"但不知道原因。

**预防**：
- **所有** `response.json()` 调用必须加 `.catch(() => ({}))`：
  ```ts
  // ❌ 危险：空 body 会崩溃
  const body = await response.json();
  
  // ✅ 安全：空 body 返回空对象，后续逻辑照常走
  const body = await response.json().catch(() => ({}));
  ```
- 链式调用也要加：
  ```ts
  // ❌ 危险
  .then(response => response.ok ? response.json() : ...)
  
  // ✅ 安全
  .then(response => response.ok ? response.json().catch(() => ({})) : ...)
  ```
- `as Type` 类型断言的写法注意括号：
  ```ts
  // ✅ 正确
  const body = (await response.json().catch(() => ({}))) as MyType;
  ```
- 用 grep 定期扫描：`grep -rn "response\.json()" src/ --include="*.tsx" | grep -v ".catch"`

### 3.2 后端返回空 body 的常见场景

1. **原生模块加载失败**：canvas/mermaid 在 Electron 环境下 require 失败，进程崩溃
2. **API 超时**：Next.js API 路由超过 `maxDuration` 被 kill
3. **中间件异常**：guard/auth 中间件抛未捕获异常
4. **内存不足**：大正文渲染（LaTeX/Mermaid）导致 OOM

## 4. UX 流程设计

### 4.1 功能不要分散在多个页面

**踩坑**：编辑器页面塞了写稿 + AI生图 + 图解生成 + 插入图片 + 排版预览入口，底部按钮一长排，用户要上下翻页找功能。

**原则**：
- 一个页面只做一件事：编辑器只管文字，预览页管图片和排版
- 功能区从上到下按操作顺序排，用户不用跳来跳去
- 入口要直接：用户应该能随时从侧边栏或底部按钮跳到下一步，不需要先完成前置条件（如"签字确认"）

### 4.2 拖拽插图交互

**踩坑**：拖图到预览页不精准、删不了、复制两张。

**根因**：
- drop 事件没有做段落级定位（只拼到末尾）
- 没有防重复机制（drop 事件短时间内重复触发）
- DOM 里的 `<img>` 没有删除按钮（用户无法移除）

**正确做法**：
- 用鼠标 Y 坐标 + `getBoundingClientRect` 算出最近的段落块，插到该块后面
- 用 `lastDropRef` 时间戳去重（300ms 内忽略重复 drop）
- 渲染后用 `useEffect` 遍历 DOM 里的 `<img>`，给每张图包一层容器 + 右上角 × 按钮

## 5. 版本管理与发版

### 5.1 覆盖安装保留数据

**问题**：用户覆盖安装新版本后，之前保存的信息（激活码、公众号配置）被删除。

**解决**：`electron-builder.yml` 加 `deleteAppDataOnUninstall: false`，卸载时不删用户数据目录。

### 5.2 版本号管理

- 每次发版前升级 `package.json` 里的 `version`
- 版本号只在这一个地方维护，`electron-builder.yml` 用 `${version}` 引用
- 旧版本安装包可以保留在 `release/` 目录，但发到夸克网盘的只保留最新版

### 5.3 强制更新预留口

- 后端授权服务器 `app.json` 里有 `latest` 版本号
- guard 守卫检查版本，`blocked=true` 时返回 HTTP 426 `update_required`
- 前端收到 426 时弹出更新提示
- 更新方式：跳夸克网盘链接下载新 exe 覆盖安装（注册码保留）

## 6. 微信公众号集成

### 6.1 推草稿的完整链路

1. 检查公众号通道（AppID/AppSecret 是否配好、token 能否获取）
2. 检查封面图（必须上传到微信永久素材库拿到 `thumb_media_id`）
3. 正文图片本机地址换成微信地址（`cdnizeLocalImages`）
4. Markdown 渲染成公众号 HTML（`markdownToWechatHtmlAsync`）
5. 按指纹判断：新建草稿 / 内容没变不重推 / 内容变了更新已有草稿
6. 调微信 API 创建/更新草稿

### 6.2 多账号支持

- `.env` 里的 `WECHAT_APPID` 是默认账号
- 额外账号存在数据库里（`readAccountById`）
- 前端多账号时显示下拉选择
- 推送前对选中账号重新测通道（通道状态跟账号走）

### 6.3 图片缓存

- 正文图片按内容指纹缓存（`draftFingerprint`）
- 指纹一致时复用上次的微信地址，不重复上传
- 失败的图片不阻断整篇，在响应里如实报回

## 7. 构建脚本链

稿台的构建脚本链有严格顺序，不能随意调整：

```
npm run build                    # Next.js 构建（Turbopack）
  ↓
copy-standalone-assets.mjs       # 清除符号链接（必须在 sanitize 之前）
  ↓
sanitize-standalone.mjs          # 清理敏感文件（白名单制）
  ↓
ensure-runtime-deps.mjs          # 补齐漏追踪的运行时依赖
  ↓
prepare-resources.mjs            # 准备 app-resources（技能包、模板等）
  ↓
ELECTRON_BUILDER_OFFLINE=true    # 离线模式避免 TLS 网络错误
npx electron-builder --win       # 打包成 exe
  ↓
verify-package.mjs               # 安全扫描（密钥、数据库、授权令牌）
```

**注意事项**：
- `ELECTRON_BUILDER_OFFLINE=true` 可以避免 electron-builder 尝试联网检查更新导致的 TLS 错误
- electron-builder 缓存在 `C:\Users\<用户>\AppData\Local\electron-builder\Cache\`（nsis、electron 二进制等）
- 如果 electron-builder 卡住，检查是否有 node 进程残留（`taskkill /F /IM node.exe`）
