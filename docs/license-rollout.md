## 一、客户端

### 1.1 激活门禁

- [ ] 实现 `POST /v1/activate` 调用，机器码按协议 §2 计算（`sha256("gaotai-v1|" + hardId + "|" + diskSerial)`）
      - **验收**：同一 code 首次激活绑定 (code, machine)；同 machine 再激活放行；不同 machine 且达 `maxDevices` → `device_limit`(403)。单测覆盖三条分支。
- [ ] 缓存令牌到 `<dataDir>/.license/token.json`（`{ token, expiresAt, machine, code, features, plan }`）
      - **验收**：重启后从缓存读取，不重新激活；文件不存在或损坏时回退到未激活态，不崩溃。
- [ ] 启动校验链：读缓存 → Ed25519 验签（内置公钥）→ 校验 `machine` 一致 → `expiresAt > now`
      - **验收**：篡改 token 任一字段 → 验签失败 → 未激活；machine 不符 → 未激活；过期 → 进入 7 天宽限期。
- [ ] 剩余有效期 < 7 天时自动 `POST /v1/refresh`；刷新失败不阻塞启动
      - **验收**：构造 `expiresAt = now + 5天` 的令牌，启动触发 refresh；mock refresh 返回 403 时不阻塞，进入宽限期。

### 1.2 未激活门禁

- [ ] `/api/*` 除白名单（`/api/license/*`、`/api/auth/*`、`/api/files/*`、`/api/health`、`/api/security/*`）外一律 `403 { "error": "not_activated", "code": "not_activated" }`
      - **验收**：未激活时 `GET /api/drafts` → 403；白名单路径正常返回。
- [ ] 激活页 UI：输入注册码 → 显示机器码（可复制）→ 调 activate → 成功展示 features/有效期
      - **验收**：手动跑通「输入码 → 激活 → 重启仍激活」。
- [ ] 未配置 `GAOTAI_LICENSE_SERVER` 时，激活页显示「未配置授权服务器」，不静默放行
      - **验收**：清空环境变量，激活页显示提示，门禁仍 403。

### 1.3 资产下发与加密

- [ ] `GET /v1/assets/manifest` + `GET /v1/assets/{name}` 拉取技能包/提示词/排版包
      - **验收**：解密后明文 JSON 的 `sha256` 与响应 `plainSha256` 一致；解密失败 → 不写入、保留旧缓存。
- [ ] AES-256-GCM 解密，密钥按协议 §5 从 token 经 HKDF-SHA256 派生；密钥不落盘、不进日志
      - **验收**：代码审查确认密钥仅在内存；日志中无 key/iv/tag/data 明文。
- [ ] 已缓存明文包在离线/令牌过期时仍可用
      - **验收**：断网启动 + 过期令牌 → 技能包/提示词仍可选用，AI 生成调用模型时才报错。

### 1.4 打包与剥离

- [ ] 打包脚本剥离 `GAOTAI_LICENSE_BYPASS` 变量（协议 §7）
      - **验收**：打包后 grep 产物中无 `GAOTAI_LICENSE_BYPASS`；设置该变量在打包版无效。
- [ ] Ed25519 公钥随客户端打包，私钥**不进**安装包、**不进** git
      - **验收**：`release/` 产物含公钥；私钥只在 `license-server/keys/` 且该目录在 `.gitignore`。
- [ ] 版本号升到 `0.2.0`（package.json、electron-builder.yml、CHANGELOG）
      - **验收**：三处版本一致为 `0.2.0`；CHANGELOG 有破坏性变更条目。

## 二、服务端

### 2.1 核心接口

- [ ] `POST /v1/activate`：绑定规则 + 限流（同 IP 5 分钟 5 次失败 → 429）
      - **验收**：curl 跑通首次绑定、重复同机放行、超限 device_limit、限流 429 四种返回。
- [ ] `POST /v1/refresh`：校验 machine → 重签令牌、更新 `lastSeenAt`
      - **验收**：machine 不符 → 403；吊销 code → 403；正常 → 新令牌 expiresAt = now+30天。
- [ ] `POST /v1/status`：返回 `{ activated, revoked, expiresAt, lastSeenAt, plan }`
      - **验收**：已激活/已吊销/未激活三种状态返回正确。
- [ ] `GET /v1/assets/manifest` + `GET /v1/assets/{name}`：Bearer token 鉴权
      - **验收**：无 token → 401；过期 token → 401；有效 token → 返回加密包。

### 2.2 领码

- [ ] `POST /v1/redeem`：同 contact 重复提交返回原码；`bad_contact`(400) / `rate_limited`(429)
      - **验收**：同 contact 二次提交 → 同一 code；空 contact → 400。
- [ ] `GET /redeem`：自包含 HTML 表单页（无外部 JS/CSS），提交到 `/v1/redeem`，成功显示码 + 复制按钮
      - **验收**：浏览器打开页面、填联系方式、提交、看到码并可复制。

### 2.3 密钥与存储

- [ ] Ed25519 私钥 `license-server/keys/ed25519-private.pem`（0600，不入库不进 git）
      - **验收**：`git status` 不追踪该文件；文件权限 0600。
- [ ] `license-server/data/license.json` 原子写（临时文件 + rename）
      - **验收**：并发写不损坏；kill 进程后文件仍可读。
- [ ] 管理员 CLI：发码、列出、吊销、解绑、查看在线（lastSeenAt）
      - **验收**：五条命令各跑通一次。

### 2.4 审计与安全

- [ ] 所有失败路径写审计日志（时间、IP、code 前 4 位、错误码），**不记完整 contact**
      - **验收**：日志中 contact 字段为前缀或哈希，无完整微信号/手机号。
- [ ] 生产 HTTPS；AppSecret 只在服务器 `.env`，权限 0600
      - **验收**：`.env` 在 `.gitignore`；`ls -l` 确认 0600；HTTP 请求被重定向到 HTTPS。

## 五、版本策略

### 5.1 本次应发 0.2.0（破坏性）

- 0.2.0 是**破坏性变更**：引入激活门禁、许可由 MIT 改为专有。按语义化版本，破坏兼容性应升 minor（0.1.x → 0.2.0）。
- CHANGELOG 的 0.2.0 条目应**置顶并明确标注 BREAKING**：
  - 「首次启动需输入注册码激活；未激活时 AI 功能不可用，本地编辑受限。」
  - 「许可证由 MIT 变更为专有许可（见 EULA）；第三方组件仍保留各自原许可证。」
- 建议在 0.2.0 发布前**冻结一版 0.1.x（如 0.1.7）作为「免激活最后版本」**，给不愿升级的用户留一个
  可用的旧版入口，同时作为回滚兜底。

### 5.2 0.1.x 用户过渡

- **0.1.x 不自动升级到 0.2.0。** 客户端应提示「0.2.0 需要注册码，旧版可继续用但不再更新」，
  让用户**主动选择**是否升级。
- 升级路径：
  1. 用户关注服务号 → 领码（§微信侧）；
  2. 下载 0.2.0 安装包覆盖安装；
  3. 首启进入激活页，粘贴注册码激活；
  4. 原 0.1.x 的本地稿件与配置在 `%APPDATA%\gaotai` 保留，0.2.0 可直接读取（数据目录不变）。
- **无注册码的 0.1.x 用户升级到 0.2.0 后会卡在激活页**，需在推广文案与服务号自动回复里把领码路径讲清楚，
  避免升级后流失。
- 0.1.x 的 MIT 许可副本继续随该版本安装包有效；我们不追溯收回已分发的 0.1.x。

## 六、防复刻的真实边界

这一节说清客户端保护能做什么、做不到什么，不要给作者或用户「绝对无法破解」的错觉。

### 6.1 客户端检查可被绕过

- 激活校验、令牌验签、资产解密都在客户端执行。有足够技术能力的人可以：
  - patch 可执行文件跳过门禁检查；
  - 用内置公钥伪造令牌（只要能替换公钥或改验签逻辑）；
  - dump 内存中已解密的资产明文。
- `GAOTAI_LICENSE_BYPASS` 剥离只能挡住「直接设环境变量」这种最低门槛，挡不住二进制修改。
- **结论**：客户端门禁是「提高门槛 + 区分善意/恶意用户」，不是不可逾越的墙。

### 6.2 真正的护城河

护城河不在客户端，而在三点：

1. **资产不进安装包。** 技能包、提示词、排版模板等核心资产由服务端加密下发，安装包里只有自研的少量内容
   和第三方 MIT 组件。未激活拿不到资产，拿到安装包也无法直接复刻完整产品。
2. **服务端渲染与鉴权。** AI 生成的提示词组装在服务端完成（正文阶段不给模型工具，方法由服务端注入，
   见 README「四道工序」），客户端只拿到最终结果。资产接口未激活返回 403。
3. **令牌时效与 lastSeenAt。** 令牌 30 天过期、刷新更新 `lastSeenAt`；服务停止即无法刷新，
   AI 功能到期失效。即便有人 dump 了资产，也只拿到某一时刻的快照，拿不到后续更新与方法演进。

### 6.3 不要说的话

- 不要在文档、文案、承诺里写「绝对无法破解」「100% 防盗版」「不可逆向」。
- 正确表述：「客户端门禁提高复刻门槛；核心资产不进安装包、由服务端鉴权下发，是主要的防护。」
- 这既是对用户的诚实，也是避免被技术社区证伪后的信任反噬。
